# คู่มือโปรเจกต์ Nestly สำหรับผู้เริ่มต้น

เอกสารนี้อธิบายว่า Nestly คืออะไร ข้อมูลไหลอย่างไร API และฐานข้อมูลมีอะไรบ้าง ตลอดจนวิธีเปิดโปรเจกต์เพื่อศึกษา โดยตั้งใจเขียนให้ผู้อ่านไม่จำเป็นต้องมีพื้นฐานเขียนโปรแกรมมาก่อน

## 1. Nestly คืออะไร

Nestly เป็นแพลตฟอร์มบริหารหอพักแบบหลายหอในระบบเดียว งานหลักที่ระบบรองรับ ได้แก่

- จัดการอาคาร ชั้น ห้อง ประเภทห้อง เฟอร์นิเจอร์ และสถานะห้อง
- จัดการผู้เช่า คำเชิญ การเข้าพัก การย้ายห้อง และการย้ายออก
- สร้างและเก็บรุ่นของสัญญาเช่า
- บันทึกมิเตอร์น้ำ/ไฟ สร้างบิล รับสลิป และตรวจการชำระเงิน
- ดูแลงานแจ้งซ่อม/ร้องเรียน พัสดุ และประกาศ
- สนทนาระหว่างผู้เช่ากับหอพัก และระหว่างหอพักกับผู้ดูแลแพลตฟอร์ม
- จัดการแพ็กเกจสมาชิก SaaS และหลักฐานการชำระค่าสมาชิก
- เก็บ audit log เพื่อทราบว่าใครทำอะไร เมื่อใด และสำเร็จหรือไม่

คำว่า “หลายหอ” หมายถึงข้อมูลแต่ละหอถูกผูกกับ `propertyId` และผู้ใช้จะอ่านหรือแก้ได้เฉพาะหอที่ตนมีสิทธิ์ เซิร์ฟเวอร์ต้องตรวจสิทธิ์นี้ทุกครั้ง ไม่ใช่อาศัยเพียงการซ่อนเมนูในหน้าเว็บ

## 2. คนสามกลุ่มที่ใช้ระบบ

| Role ในโค้ด | เรียกแบบง่าย | ทำอะไรได้โดยสรุป |
|---|---|---|
| `SUPER_ADMIN` | ผู้ดูแลแพลตฟอร์ม | ดูแลบัญชีเจ้าของหอ หอพัก แพ็กเกจสมาชิก การชำระค่าสมาชิก และ audit log |
| `PROPERTY_ADMIN` | เจ้าของ/ผู้ดูแลหอ | จัดการข้อมูลภายในหอ ห้อง ผู้เช่า สัญญา บิล มิเตอร์ งานแจ้งเรื่อง พัสดุ ประกาศ และการตั้งค่า |
| `TENANT` | ผู้เช่า | ดูข้อมูลห้อง/สัญญา/บิล ส่งสลิป รับประกาศ ดูพัสดุ แจ้งเรื่อง และแชทกับหอ |

ผู้ใช้หนึ่งคนมี role หลักหนึ่งแบบ เจ้าของหออาจมี `PropertyMembership` หลายรายการเพื่อดูแลหลายหอ ส่วนผู้เช่าจะเชื่อมกับห้องผ่าน `RoomOccupancy` ไม่ได้เชื่อมกับห้องด้วยข้อความธรรมดา

## 3. ภาพรวมการทำงานหนึ่งครั้ง

ตัวอย่างเมื่อผู้เช่ากดดูบิล:

```text

   │  GET /api/v1/tenant/invoices
   ▼

   │
   ├──ตรวจ session, role และห้องที่ผู้เช่าพัก
   ▼
Service / business logic
   │
   ▼
Repository / Prisma ─────────► PostgreSQL
   │
   ▼
เลือกเฉพาะข้อมูลที่อนุญาต แล้วส่ง JSON กลับไปแสดงบนหน้าเว็บ
```

แนวคิดสำคัญคือหน้าเว็บมีหน้าที่แสดงผลและรับการกด ส่วนการตัดสินว่า “ทำได้หรือไม่” ต้องอยู่บนเซิร์ฟเวอร์เสมอ

## 6. API มีเท่าไร และดูได้ที่ไหน

ณ วันที่สร้างเอกสารนี้ โค้ดมี:

- **114 URL API** หรือ 114 ไฟล์ `route.ts`
- **144 HTTP operations** เมื่อนับ method แยกกัน เช่น URL เดียวรองรับทั้ง `GET` และ `POST` จะนับเป็นสองการทำงาน
- API แบ่งหลัก ๆ เป็น auth/account, Owner/Admin, Tenant, Super Admin, chat, documents, health และ internal jobs

รายชื่อครบทุก URL พร้อม method และหน้าที่ระดับภาพรวมอยู่ที่ [API_ENDPOINTS_TH.md](./API_ENDPOINTS_TH.md) และสร้างใหม่จากโค้ดได้ด้วย:

```bash
npm run docs:api
```

สัญญาทางเทคนิคของ API หลัก เช่น parameter, request body, response และ status code อยู่ที่ [openapi.json](./openapi.json) ตรวจความถูกต้องได้ด้วย `npm run openapi:check`

ความหมายของ method แบบสั้น:

- `GET` อ่านข้อมูล โดยหลักไม่ควรเปลี่ยนข้อมูล
- `POST` สร้างรายการหรือสั่งให้เกิดกระบวนการ
- `PUT` แทนข้อมูลชุดเดิมทั้งชุด
- `PATCH` แก้เฉพาะบางฟิลด์หรือเปลี่ยนสถานะ
- `DELETE` ลบ ยกเลิก หรือปิดรายการตามกฎธุรกิจ

## 7. ฐานข้อมูลเก็บอย่างไร

PostgreSQL เก็บข้อมูลเป็น “ตาราง” เปรียบเหมือนชีตหลายแผ่นที่เชื่อมกันด้วย ID ตัวอย่างเช่น `Invoice.roomId` ชี้ว่าบิลเป็นของห้องใด และ `Room.propertyId` ชี้ว่าห้องอยู่ในหอใด

โครงสร้างจริงอยู่ใน `prisma/schema.prisma` ปัจจุบันมี **44 models (ตารางเชิงโดเมน)**, 29 enums และ migration 21 รุ่น ตารางถูกแบ่งให้เข้าใจง่ายได้ดังนี้

## 8. ไฟล์จริงเก็บที่ไหน

ไฟล์ PDF, สลิป, รูปพัสดุ และไฟล์แนบไม่เก็บเป็น binary ใน PostgreSQL ฐานข้อมูลเก็บเพียง metadata เช่น `storageKey`, ชื่อไฟล์, MIME type, ขนาด, checksum และเจ้าของข้อมูล ส่วน bytes ของไฟล์อยู่ใน storage adapter

| ค่า `STORAGE_TYPE` | ตำแหน่งไฟล์ |
|---|---|
| `local` | โฟลเดอร์ที่ `LOCAL_STORAGE_PATH` กำหนด ค่าเริ่มต้นคือ `./storage/documents` เหมาะกับการพัฒนา |
| `s3` | Amazon S3 bucket ที่ระบุด้วย `AWS_REGION`, `AWS_S3_BUCKET` และ `AWS_S3_PREFIX` เหมาะกับ deployment หลายเครื่อง |

ก่อน upload ต้องตรวจชนิดไฟล์จริง ขนาด จำนวนไฟล์ และสิทธิ์ของผู้ใช้ ชื่อ/ตำแหน่งจาก browser เชื่อถือไม่ได้ การดาวน์โหลดไฟล์ส่วนตัวต้องผ่าน authorized endpoint ไม่ควรเปิด storage path ตรง ๆ

ระบบมี retention job ล้างไฟล์ที่หมดอายุตาม `DOCUMENT_RETENTION_DAYS`, `SLIP_RETENTION_DAYS` และ `CHAT_ATTACHMENT_RETENTION_DAYS` โดยเก็บหลักฐานในฐานข้อมูลว่าไฟล์ถูกล้างเมื่อใด

## 9. การเข้าสู่ระบบและการป้องกันข้อมูล

- cookie session ชื่อ `dorm_session` มีอายุ 8 ชั่วโมง
- cookie เป็น `HttpOnly`, ใช้ `SameSite=Lax` และเปิด `Secure` ใน production จึงไม่ควรนำ token ไปเก็บใน `localStorage`
- token จริงถูกส่งใน cookie แต่ฐานข้อมูลเก็บเฉพาะ SHA-256 hash
- รหัสผ่านเก็บเป็น password hash ไม่เก็บ plaintext
- บัญชีต้อง active, ได้รับอนุมัติ และ session ยังไม่หมดอายุ
- route สำคัญตรวจ role และ ownership/property membership ทุกครั้ง
- state-changing request ตรวจ origin เพื่อลด CSRF และ endpoint ที่เสี่ยงมี rate limiting
- input จาก request, URL, cookie, upload และ environment ต้องผ่าน schema validation
- ข้อผิดพลาดที่ส่งให้ผู้ใช้ไม่ควรเปิดเผย stack trace, SQL, path ภายใน หรือความลับ

สิ่งเหล่านี้เป็นแนวป้องกันที่โค้ดตั้งใจใช้ ไม่ได้หมายความว่าระบบ “ปลอดภัยสมบูรณ์” การ deploy จริงยังต้องตั้ง HTTPS, CSP, database permission, S3 policy, backup, monitoring และ secret manager ให้เหมาะกับสภาพแวดล้อม

## 10. Environment ที่ต้องรู้

คัดลอก `.env.example` เป็น `.env` เฉพาะในเครื่องของตน และห้าม commit ค่าจริง กลุ่มค่าหลักคือ:

- แอปและฐานข้อมูล: `APP_URL`, `DATABASE_URL`
- storage: `STORAGE_TYPE`, `LOCAL_STORAGE_PATH`, `AWS_REGION`, `AWS_S3_BUCKET`, `AWS_S3_PREFIX`
- งาน maintenance: `JOB_SECRET` และจำนวน/อายุ retention
- reset password/email: `RESEND_API_KEY`, `PASSWORD_RESET_EMAIL_FROM`
- บัญชีเริ่มต้นสำหรับ development: ตัวแปร `BOOTSTRAP_*` และ `DEMO_*`; ห้ามใช้ค่าเดาง่ายใน production
- browser test: `PLAYWRIGHT_BASE_URL`

ไฟล์ `lib/server/env.ts` เป็นจุดตรวจว่าค่าที่จำเป็นครบและอยู่ในรูปแบบถูกต้อง

## 11. วิธีเปิดโปรเจกต์ในเครื่องพัฒนา

ต้องมี Node.js รุ่นที่รองรับโปรเจกต์, PostgreSQL และ npm จากนั้น:

```bash
# 1) ติดตั้ง dependency และสร้าง Prisma client
npm install

# 2) สร้าง .env จากตัวอย่าง แล้วแก้ DATABASE_URL และค่าที่จำเป็น
cp .env.example .env

# 3) สร้าง/อัปเดตตารางฐานข้อมูลสำหรับเครื่องพัฒนา
npm run db:migrate

# 4) เปิดเว็บ
npm run dev
```

เปิด URL ที่ terminal แสดง โดยทั่วไปคือ `http://localhost:3000` ไม่ควรใช้ฐานข้อมูล production ในการพัฒนาหรือทดสอบ

## 13. วิธีเปลี่ยนฐานข้อมูลอย่างปลอดภัย

1. แก้ `prisma/schema.prisma`
2. สร้าง migration ใหม่ด้วย `npm run db:migrate`
3. ตรวจ SQL ที่ Prisma สร้าง โดยเฉพาะคำสั่งลบ/แปลงข้อมูล
4. ทดสอบด้วยฐานข้อมูลแยก
5. สำรองข้อมูลและวางแผน rollback ก่อน deploy การเปลี่ยนแปลงสำคัญ

ห้ามแก้ไฟล์ใน `prisma/migrations` ที่เคยรันแล้ว เพราะ checksum และประวัติของฐานข้อมูลจะไม่ตรงกัน และห้ามรัน destructive migration กับ production โดยไม่มีการยืนยันชัดเจน

## 14. คอมเมนต์ในซอร์สโค้ด

ไฟล์ซอร์สและ configuration ที่ทีมดูแลเองมีหัวข้อ `คำอธิบายสำหรับผู้เริ่มต้น` บอก “ไฟล์นี้คืออะไร” และ “ทำงานอย่างไร” ปัจจุบันมีคำอธิบายระดับหัวไฟล์ 358 ไฟล์ผ่าน:

```bash
npm run docs:annotate
```

นอกจากนี้มี JSDoc ภาษาไทยอยู่เหนือ function, React component, method, class, interface, type, enum และ schema สำคัญ 1,612 ก้อนในไฟล์โค้ด 307 ไฟล์ รวมถึงคำอธิบาย model/enum ใน Prisma สร้างและอัปเดตได้ด้วย:

```bash
npm run docs:annotate:symbols
```

คอมเมนต์แต่ละก้อนบอกหน้าที่ ค่าที่รับ และผลลัพธ์ เพื่อให้ผู้อ่านใหม่รู้ว่าควรเริ่มอ่านตรงไหน สคริปต์ทั้งสองรันซ้ำได้และไม่สร้างคอมเมนต์ซ้ำ หากเพิ่ม function ใหม่ให้รันสองคำสั่งนี้อีกครั้ง ส่วนกฎที่ซับซ้อนยังควรเขียนคอมเมนต์ด้วยคนใกล้โค้ดเพื่ออธิบาย “เหตุผล” ของกฎนั้น ไม่ใช่เพียงทวนทุกบรรทัด

ไฟล์ที่จงใจไม่เติมคอมเมนต์:

- `generated/prisma/**` เพราะ Prisma เขียนทับเมื่อ generate
- `prisma/migrations/**` เพราะเป็นประวัติที่มี checksum และไม่ควรเปลี่ยนย้อนหลัง
- `node_modules/**`, `.next/**`, report/coverage เพราะเป็นไฟล์จากเครื่องมือ
- JSON, lockfile, รูป, font, PDF และไฟล์สื่อ เพราะรูปแบบไม่อนุญาตหรือคอมเมนต์ไม่มีประโยชน์
- เอกสารใน `docs` ใช้หัวข้อและคำอธิบายในเนื้อหาแทน code comment

## 15. เมื่อจะเพิ่ม feature ใหม่ ควรเริ่มตรงไหน

1. เขียนกฎธุรกิจและ validation ใน `lib/domain` หรือโมดูล server ที่เหมาะสม
2. ให้ repository/service เป็นผู้ติดต่อ Prisma แทน UI
3. เพิ่ม API route และตรวจ session, role, property ownership และ input บนเซิร์ฟเวอร์
4. สร้าง component/page สำหรับแสดงผล พร้อม loading, empty, error, success และ disabled states
5. เพิ่ม tests ทั้งกรณีที่อนุญาตและต้องปฏิเสธ โดยเฉพาะการข้าม role หรือเข้าถึง property ของคนอื่น
6. รัน `npm run docs:annotate`, `npm run docs:annotate:symbols`, `npm run docs:api` และชุดตรวจคุณภาพ

## 17. คำศัพท์สั้น ๆ

| คำ | ความหมาย |
|---|---|
| API | ช่องทางที่หน้าเว็บหรือระบบอื่นใช้ขอข้อมูล/สั่งงานจากเซิร์ฟเวอร์ |
| Endpoint | URL API หนึ่งเส้นทางรวมกับ method |
| Model/Table | โครงสร้างเก็บข้อมูลชนิดหนึ่งในฐานข้อมูล |
| Record/Row | ข้อมูลหนึ่งรายการในตาราง เช่น บิลหนึ่งใบ |
| Foreign key/Relation | ตัวเชื่อมว่ารายการหนึ่งเป็นของหรือเกี่ยวกับอีกรายการใด |
| Migration | ขั้นตอนเปลี่ยนโครงสร้างฐานข้อมูลจากรุ่นหนึ่งไปอีกรุ่น |
| Session | หลักฐานชั่วคราวหลัง login ว่าคำขอมาจากบัญชีใด |
| Role/RBAC | การแบ่งสิทธิ์ตามประเภทผู้ใช้ |
| Validation | การตรวจชนิด รูปแบบ ความยาว และกฎของข้อมูลก่อนใช้ |
| Storage key | ชื่ออ้างอิงไฟล์ใน local storage/S3 ไม่ใช่ URL สาธารณะ |
| Audit log | บันทึกเหตุการณ์สำคัญสำหรับติดตามและตรวจสอบย้อนหลัง |
