## 1. ภาพรวม

**Nestly** คือระบบจัดการหอพักแบบ SaaS หลายหอ มี 3 บทบาท

| บทบาท | เส้นทางหลัก | ใช้ทำอะไร |
|---|---|---|
| แอดมินใหญ่ (Super Admin, "Nestly Control") | `/super-admin` | อนุมัติบัญชีเจ้าของหอ จัดการหอ แพ็กเกจ ตรวจสลิปค่าสมาชิก Audit Log และตั้งค่าบัญชีรับเงินของบริษัท |
| เจ้าของหอ (Property Admin) | `/admin/properties/<id>/…` | ผังห้อง ผู้เช่า สัญญา มิเตอร์ บิลและใบเสร็จ แจ้งซ่อม/ร้องเรียน พัสดุ ประกาศ และตั้งค่าหอ |
| ผู้เช่า (Tenant) | `/tenant/…` | บิล ชำระเงิน ใบเสร็จ สัญญา ประกาศ พัสดุ แจ้งเรื่อง และบัญชี |

- **เว็บจริง:** https://nestlyspace.tech (deploy บน VPS ผ่าน GitHub Actions)

## 2. เทคโนโลยี

- **เว็บ:** Next.js 16.4 (App Router, Turbopack), React 19, TypeScript strict และ Tailwind CSS v4
  - Next รุ่นนี้ต่างจากที่คุ้นเคย อ่านเอกสารใน `node_modules/next/dist/docs/` ก่อนแก้ส่วนที่เกี่ยวกับ Next
- **ฐานข้อมูล:** PostgreSQL กับ Prisma 7 (client generate ไปที่ `generated/`)
- **ตรวจข้อมูลเข้า:** Zod 4 ฝั่งเซิร์ฟเวอร์
- **ล็อกอิน:** session เก็บใน cookie แบบ HttpOnly
- **อีเมล:** Resend เรียกผ่าน `fetch` ตรงๆ ไม่มี dependency เพิ่ม
- **PDF:** สร้างจาก HTML Template ด้วย Chromium (Puppeteer)
- **ทดสอบ:** Vitest แยกเป็น unit กับ integration และ Playwright สำหรับ E2E
- **รันระบบ:** Docker Compose และ GitHub Actions (CI → Deploy)

## 3. โครงสร้างโปรเจกต์ที่ต้องรู้

| ที่อยู่ | มีอะไร |
|---|---|
| `app/` | หน้าและ API route (`app/api/v1/...`) |

| `lib/server/` | service ที่แตะฐานข้อมูล, auth, จัดการ error (`api.ts`) |
| `lib/server/email.ts` | ตัวส่งอีเมลกลาง ทุกอีเมลต้องส่งผ่านตัวนี้ |
| `lib/documents/` | ระบบเอกสาร PDF (สัญญา ใบแจ้งหนี้ ใบเสร็จ) |
| `lib/repositories/` | query ที่ใช้ซ้ำ |
| `lib/client/` | hook และตัวช่วยฝั่งเบราว์เซอร์ |
| `prisma/schema.prisma`, `prisma/migrations/` | โครงสร้างฐานข้อมูล ทุกการเปลี่ยนต้องมี migration |
| `scripts/` | seed เดโม, สร้างแอดมินแรก, งาน maintenance, สคริปต์ OpenAPI |
| `docs/openapi.json` | เอกสาร API ที่ CI ตรวจว่าตรงกับ route จริง |
| `tests/integration/`, `tests/e2e/` | เทสต์ที่ต้องใช้ฐานข้อมูลจริง |
| `app/globals.css` | สไตล์กลาง เขียนเป็น `@apply` ใน `@layer components` |

> unit test ต้องอยู่ใต้ `lib/` เท่านั้น (`vitest.config.ts` รวมแค่ `lib/**/*.test.ts`) ถ้าต้องทดสอบฟังก์ชันในคอมโพเนนต์ ให้ย้ายฟังก์ชันนั้นไปไว้ใน `lib/` ก่อน

## 6. ทำงานร่วมกัน 2 คน และการ Deploy

**ก่อนเริ่มงานทุกครั้ง:**

```bash
git fetch origin
```

```bash
git log --oneline HEAD..origin/main
```

- ถ้ามีงานใหม่ของเพื่อน ให้ดึงมาก่อน (`git merge --ff-only origin/main` หรือ rebase)
- ดึงมาแล้วรัน `npx prisma migrate deploy` เสมอ เพราะเพื่อนก็เพิ่ม migration และรีสตาร์ท dev server ด้วย
- เพื่อนทำงานผ่าน PR ส่วนเจ้าของงานฝั่งนี้ push เข้า `main` ตรงๆ ถ้าเห็น PR ค้าง ให้แจ้งเพื่อนรวม `main` ล่าสุดก่อน merge จะได้ไม่ทับงานกัน

**ก่อน push ทุกครั้ง:**
1. `git fetch origin` อีกรอบ ถ้า `main` มีงานใหม่ให้รวมก่อน ห้าม push ทับ
2. รัน typecheck, lint, `npm run openapi:check`, unit และ integration test
3. ถ้าเพิ่ม API ใหม่: รัน `npm run openapi:sync` แล้วเพิ่มรูปคำตอบใน `scripts/openapi-response-contracts.mjs` และรูปคำขอใน `scripts/openapi-request-contracts.mjs` (route ที่ตอบเป็นไฟล์ ให้เพิ่มใน `isBinaryGet` ของ `scripts/sync-openapi-v1.mjs`) สคริปต์รันบน Windows ได้แล้ว
4. ตรวจว่าไม่มีรหัสผ่านหรือค่าลับติดไปใน diff และไม่ commit `.env`, `.claude/`, `deliverables/` หรือ `AGENTS.md` ที่ `next dev` แก้เอง
5. push แบบ fast-forward: `git push origin HEAD:main`

**Deploy:**
- **ลำดับ:** push เข้า `main` → workflow **CI** รัน (audit, quality, integration, E2E, docker) → ถ้าผ่าน workflow **Deploy** รันต่อเองด้วย `workflow_run` → SSH เข้า VPS → `docker compose pull` + `up -d`
- CI ใช้เวลาราว 10–13 นาที Deploy อีกราว 4–8 นาที ถ้า CI ไม่ผ่านจะไม่ deploy
- **migration:** container `migrate` รัน `prisma migrate deploy` ทุกครั้งที่ deploy migration ที่เข้า `main` จึงไปรันกับฐานข้อมูลจริงเอง
  - migration ที่แก้ข้อมูลต้องเขียนให้ไม่ลบอะไร และรันซ้ำได้
  - อธิบายไว้ในไฟล์ SQL ว่าแตะแถวไหนบ้าง
  - ต้องบอกเจ้าของงานให้ชัดก่อน push
- **ดูสถานะ:** https://github.com/Catboyz-45/it-project/actions (ต้องล็อกอิน GitHub ถึงจะเห็น log)
- ขั้นตอน VPS แบบละเอียดอยู่ใน `docs/DEPLOY_VPS_TH.md`

## 7. ธรรมเนียมที่ต้องทำตาม

**ทั่วไป**
- **คอมเมนต์:** ภาษาไทย อธิบายว่า "ทำไม" ไม่ใช่ "ทำอะไร" เขียนตามสไตล์ไฟล์รอบข้าง
- **ข้อความ UI:** ภาษาไทยทั้งหมด
- **ข้อมูลเข้า:** ตรวจด้วย Zod ทุกครั้ง ใช้ `.strict()` และใช้ `recordIdSchema` (cuid) กับ id ใน URL ดังนั้น id ที่ไม่ใช่รูปแบบ cuid จะได้ 404 เสมอ
- **ID ข้อมูลเดโม:** สร้างด้วย `demoId()` ใน `scripts/demo-ids.mjs` (`'c' + md5('nestly-demo:' + key)`)

**API และความปลอดภัย**
- ทุก route ใช้ `apiErrorResponse` และ route ที่เปลี่ยนข้อมูลเรียก `assertSameOrigin` กัน CSRF
- `assertSameOrigin` บังคับ `Content-Type: application/json` กับ**ทุก**คำขอที่เปลี่ยนข้อมูล รวมถึง DELETE ที่ไม่มี body ฝั่งเบราว์เซอร์จึงต้องส่ง header นี้เสมอ ไม่งั้นได้ 415 (ปุ่มยกเลิกคำเชิญเคยพังเพราะเรื่องนี้)
- ตรวจสิทธิ์ที่เซิร์ฟเวอร์เสมอด้วย `requireRequestAuth` และ `requireRole` และตรวจว่าข้อมูลเป็นของหอหรือของผู้เช่าคนนั้นจริง โดยใส่เงื่อนไขไว้ใน query เลย
- ข้อผิดพลาด 4xx เป็นข้อความที่ตั้งใจบอกผู้ใช้ ส่วน 5xx จะแนบรหัสอ้างอิงให้ผู้ใช้แจ้งทีมงาน

**อีเมล**
- ส่งผ่าน `sendEmail()` ใน `lib/server/email.ts` เท่านั้น ห้ามเรียก Resend ตรง
- รหัสหรือโทเคนในลิงก์ใส่หลัง `#` (เช่น `/register#code=...`) ไม่ใส่ใน `?` เพราะส่วนหลัง `#` เบราว์เซอร์ไม่ส่งไปที่เซิร์ฟเวอร์ จึงไม่ค้างใน log
- ส่งไม่ผ่านต้องไม่ทำให้งานหลักพัง ให้บันทึกด้วย `logEmailFailure()` (ห้ามใส่อีเมลผู้รับหรือโทเคนใน log)
- งานที่ส่งซ้ำได้ เช่นอีเมลเตือน ต้อง "จอง" แถวในฐานข้อมูลก่อนส่ง กันงานสองรอบส่งซ้ำ

**เอกสาร PDF**
- ข้อมูลในใบเสร็จต้องสร้างจากบิลในฐานข้อมูลฝั่งเซิร์ฟเวอร์เท่านั้น ห้ามรับยอดจากเบราว์เซอร์
- เพิ่มชนิดเอกสารใหม่ต้องแก้ครบ 5 ที่: enum `DocumentKind` ใน schema พร้อม migration, `documentKinds` ใน `lib/documents/types.ts`, schema และชื่อช่องใน `placeholders.ts`, Template ตั้งต้นใน `default-templates.ts` และชื่อการ์ดใน `DocumentTemplatePanel.tsx`
- หอที่ยังไม่มี Template ของตัวเอง ระบบใช้ของตั้งต้นให้อัตโนมัติ

**หน้าเว็บ**
- **Tailwind:** คลาส utility ที่ใส่ตรงใน JSX จะชนะกฎใน `@layer components` เสมอ ถ้าจะทับด้วย CSS ของคอมโพเนนต์ ต้องย้าย utility นั้นออกหรือใช้ `max-md:` แทน
- **ค่าคงที่:** ห้าม export ค่าคงที่จากไฟล์ `"use client"` ไปให้ Server Component ใช้ เพราะจะได้ตัวอ้างอิงของ client แทนค่าจริง และ typecheck จับไม่ได้ ให้วางค่าไว้ใน `lib/domain/` แทน
- **grid ที่ต้องหดตามจอ:** ใส่ `grid-cols-[minmax(0,1fr)]` ไม่งั้นคอลัมน์จะยืดตามข้อความยาวจนล้นจอมือถือ
- **ป็อปอัพ:** ทุกตัวใช้ `components/ui/Dialog.tsx` ส่วนกล่องยืนยันใช้ `useConfirmation()` หรือ `ConfirmationDialog`
- **ตารางในหน้าจัดการ:** หัวตารางต้องตรึงไว้ และคอลัมน์แรกต้องปักไว้ซ้าย (มีเทสต์ `table-contract.spec.ts` ตรวจ)

## 8. ระบบออกแบบ UI ปัจจุบัน

- **ป็อปอัพบนคอม:** แบบ YouTube มุมโค้ง 12px ไม่มีแถบเทาท้ายกล่อง ปุ่มทรงแคปซูล ปุ่มรองพื้นเทา `#f2f2f2`
- **ป็อปอัพบนมือถือ (≤767px):** กล่องฟอร์มเป็น bottom sheet มีขีดจับด้านบน ส่วนกล่องยืนยันเป็นแบบ iOS alert
- **ปุ่มบัญชีท้ายแถบเมนู (ทุกบทบาท):** วงกลมตัวย่อชื่อ + ชื่อ + ป้ายบทบาท (เจ้าของหอสีม่วง ผู้เช่าสีเขียว แอดมินใหญ่สีเหลือง) ตอนย่อแถบเหลือแค่วงกลม
  - เจ้าของหอมีแถว "ตั้งค่าหอ" (ไอคอนเฟือง) แยกอยู่เหนือปุ่มบัญชี
  - ตัวย่อชื่ออยู่ใน `lib/account-initials.ts` รองรับชื่อไทย (ข้ามสระหน้า)
- **หน้าผู้เช่าบนมือถือ:**
  - ใช้แถบเมนูล่าง 5 ปุ่ม และปุ่ม "เพิ่มเติม" ที่มีเมนูสัญญา ประกาศ บัญชี และออกจากระบบ
  - ไม่มีปุ่มแฮมเบอร์เกอร์
  - responsive มือถือเน้นเฉพาะส่วนผู้เช่า
- **เมนูข้างของแอดมินใหญ่และเจ้าของหอ:** ย่อเป็นแถบไอคอนได้บนคอม บนมือถือเป็นลิ้นชักที่เปิดจากปุ่มแฮมเบอร์เกอร์
- **หน้าการชำระสมาชิกของแอดมินใหญ่:** แบบ Google Admin มีการ์ดสรุป ช่องค้นหาที่แนะนำคำระหว่างพิมพ์ ชิปกรองสถานะ ตารางหน้าละ 12 รายการ และแผงสลิปด้านขวา
- **รหัสผ่าน:** ทุกฟอร์มมีรายการกฎพร้อมเครื่องหมายถูก (`PasswordRequirements`) กฎคือ 12 ตัวขึ้นไป มีพิมพ์ใหญ่ พิมพ์เล็ก และตัวเลข
- **ช่องกรอกที่มีหน่วย:** หน่วยอยู่ในช่องชิดขวา (`UnitInput`)

## 10. งานที่ยังค้าง (เรียงตามที่แนะนำ)

1. **สวิตช์เปิด/ปิดเมนูตามแพ็กเกจ** (พัสดุ ประกาศ แจ้งซ่อม) ตอนนี้มีแค่ `allowPromptPay`, `allowFileUploads`, `allowPrioritySupport`
   - ลบแพ็กเกจได้เฉพาะตัวที่ไม่มีหอใช้
   - ตั้งโควตาห้องเป็น "ไม่จำกัด" ได้
2. **ระงับบัญชีเจ้าของหอรายคน** ตอนนี้ระงับได้ทั้งหออย่างเดียว
3. **สถานะห้อง "จอง"** ยังไม่มี
4. **แจ้งซ่อม:** เพิ่มช่องค่าใช้จ่ายซ่อม และช่องเวลาที่สะดวก
5. **พัสดุ:** QR ให้ผู้เช่ายื่น และหน้าสแกนรับของฝั่งหอ
6. **เก็บกวาด:**
   - หน้าบัญชีผู้เช่ายังไม่มีปุ่ม "ลืมรหัสผ่าน"
   - `components/dorm/TenantEditModal.tsx` เป็นโค้ดค้าง ไม่มีปุ่มไหนเปิดได้
   - เลขบัตรประชาชนยังเก็บแบบไม่เข้ารหัส
   - schema คำตอบของการสร้างคำเชิญใน `docs/openapi.json` ยังไม่ตรงกับของจริง

> ถ้าแบ่งงานกับเพื่อน ให้แบ่งเป็นข้อๆ จะได้ไม่แก้ไฟล์เดียวกัน

## 11. แก้ปัญหาที่เจอบ่อย

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| `Invalid value for argument ...` หรือฟังก์ชัน Prisma "is not a function" หลังดึงงานหรือเพิ่ม migration | dev server ยังใช้ Prisma client ตัวเก่า | `npx prisma generate` แล้วรีสตาร์ท dev server |
| `Another next dev server is already running` | เปิด dev server ซ้อนในโฟลเดอร์เดียวกัน | ปิดตัวเก่าก่อน หรือใช้ `next start` กับ port อื่นตอนรัน E2E |
| API ตอบ 404 ทั้งที่ข้อมูลมีอยู่ | id ไม่ใช่รูปแบบ cuid | ใช้ id จริงจากฐานข้อมูล ข้อมูลเดโมต้องสร้างด้วย `demoId()` |
| ปุ่มที่ส่ง DELETE/PATCH ได้ 415 | ไม่ได้ส่ง `Content-Type: application/json` | ใส่ header นี้ทุกครั้งที่เปลี่ยนข้อมูล |
| CI หมวด quality ไม่ผ่านที่ `openapi:check` | เพิ่ม API แต่ไม่ได้ลงเอกสาร | ทำตามข้อ 3 ของ "ก่อน push" ในหมวด 6 |
| หน้าเว็บพังเพราะค่าคงที่กลายเป็น function | import ค่าจากไฟล์ `"use client"` ไปใช้ใน Server Component | ย้ายค่าไปไว้ใน `lib/domain/` |
| ภาพหน้าจอจากหน้าต่างเบราว์เซอร์ในแอปไม่ตรงหรือค้าง | หน้าต่างถูกซ่อน animation ไม่ทำงาน | วัดด้วย JavaScript หรือถ่ายภาพด้วย Playwright แบบ headless แทน |
| ใบเสร็จ หรือ PDF พังครั้งแรก | หอยังไม่มี Template | ระบบใช้ของตั้งต้นให้อยู่แล้ว ถ้ายังพังให้ดู log ฝั่งเซิร์ฟเวอร์ (Chromium อาจไม่พร้อม) |
| อีเมลไม่ถูกส่งในเครื่อง | ยังไม่ได้ตั้งค่า Resend | ปกติของ dev ระบบข้ามเงียบๆ ตั้ง `RESEND_API_KEY` ถ้าต้องการส่งจริง |

## 12. วิธีทำงานกับเจ้าของงาน

- **ภาษา:** สื่อสารเป็นภาษาไทย อธิบายแบบง่าย ไม่ใช้ศัพท์เทคนิคเกินจำเป็น
- **งานดีไซน์:** มักขอให้ "เสนอแบบที่นิยมมาหลายๆ แบบ" เช่นแบบ Google, YouTube, GitHub, Stripe ให้ทำตัวอย่างภาพเปรียบเทียบ 3–4 แบบก่อน แล้วรอให้เลือกค่อยลงมือ
- **ฟังก์ชัน:** ต้องครบเสมอ ("ฟังก์ชันมีให้ครบ") เปลี่ยนหน้าตาแล้วห้ามทำฟังก์ชันเดิมหาย
- **ตรวจงาน:** ดูจากภาพหน้าจอของเว็บจริงและจอขนาด iPhone 16 (393×852) แก้แล้วให้ตรวจในเบราว์เซอร์จริงทุกครั้ง ไม่ใช่แค่ผ่านเทสต์
- **commit/push:** ทำเมื่อเจ้าของงานสั่งเท่านั้น ฝั่งนี้ push เข้า `main` ได้เลยไม่ต้องเปิด PR แต่ต้องดึงงานของเพื่อนมาก่อนทุกครั้ง
- **migration ที่แตะข้อมูลจริง:** ต้องบอกให้ชัดก่อน push
- **ข้อมูลทดสอบในฐานข้อมูลเครื่อง:** ถ้าสร้างเพิ่มเพื่อลองหน้าจอ ต้องลบออกหลังใช้ และห้ามกดอนุมัติหรือเปลี่ยนสถานะข้อมูลเดโมโดยไม่จำเป็น
